# Code-Addition Checklist

Answered by `/rfp` (per story) and `spec-plan` (per plan) before tasks are final; `/review-diff` checks the diff against it. A repo's `.claude/rules/code-addition-checklist.md` supplies the concrete answers (real infra tiers, CLI, test layers, shared-library packages, generators) — follow it when present. A "yes" to 1, 2, 5, 6, or 9 is its own task, not an afterthought; 10 and 11 are answered for every story and plan.

**The One Idea** (the target shape for 3, 7, 8): everything is an implementation detail behind an interface, selected by configuration, injected explicitly, and wrapped by decorators.

1. **Cross-cutting / infra?** Walk `~/.claude/templates/cross-cutting.md`: every layer this change reaches (contracts, data, config, secrets, permissions, network, build, CI/CD, IaC, deploy, env parity, observability) is done, not needed with a reason, or a gap — and the rollout order is stated. A dev-environment change and a staging/prod (IaC) change?
2. **CLI/tooling?** A change to the project's CLI or task runner? A step that only runs a stock tool (`golangci-lint`, `helm`, `buf`, `pytest`, `tilt`) is a `justfile`/`Makefile` recipe, not Go code with its own tests; a CLI command holds only logic no tool provides.
3. **Philosophy / gold standard?** Consistent with the project's design philosophy, and following a named reference implementation whose code is excerpted verbatim in the story or plan, including a test exemplar? Code that violates current standards isn't gold. A deviation is an ADR, not a silent exception.
4. **Right test types, right double** (`testing.md` *Test Double Policy*)? Unit / integration / e2e, plus property/fuzz and chaos when warranted. An integration test **names its Docker image + testcontainers module** (e.g. `postgres:16` via `testcontainers-go` / `testcontainers[postgres]` / `@testcontainers/postgresql`).
5. **Config?** Which impl runs is a `Kind` in layered, typed, validated config (`base` → env overlay → gitignored secrets; env vars override) — never a hard-coded import or an env read in a constructor. A field exists only when some environment really sets a different value; otherwise it's a constant. Every field has a fail-safe `base` default and a doc string, and the schema validates it — no per-field default tests.
6. **Can it be generated?** A contract (proto, OpenAPI, GraphQL, schema, DI graph, enum, mock) the code is derived from? Then edit the source and run the project's generator through its CLI — never hand-write or hand-edit the output. A third repetition of one shape is a scaffold/template (`text/template` + `//go:embed`, Jinja, a codegen subcommand), not copy-paste. The seam ceremony in 7–8 is the first candidate: declare it, generate it.
7. **One-Idea shape — at a seam?** For an external boundary or a component with two real backends: a core interface; impls chosen by a `Kind` + `Config` + `*_from_config` / `NewFromConfig` factory that returns the interface, defaults to a stub/noop (the graph boots with zero infra), and fails loudly on an unknown kind; constructor injection wired at the composition root. An internal collaborator with one implementation is a concrete type, injected the same way — no interface, mock, or `Kind` until a second implementation exists.
8. **Resilient and observable?** Every external call has a chosen timeout; retry (backoff + jitter, transient errors only), circuit breaker, logging, tracing, metrics are **decorators** in the per-layer order, applied at the composition root — never inlined. Errors carry a code (transient/permanent, transport status derive from it). Structured logs with trace correlation; health/readiness; graceful shutdown.
9. **Reuse shared abstractions?** DRY means push logic down into the shared library and inject product strategy up — Strategy / Decorator / Factory / Adapter / Repository over a grab-bag helper. A generic gap is fixed in the shared library, not forked locally — and a new generic capability is **born** there: building it in the product first cost ~300K deleted lines when it moved.
10. **Budget?** Estimate the hand-written code lines (production + test; docs and comments are not counted) and say what the change deletes. Prefer the version with fewer hand-maintained lines within the shape: a stock tool over a wrapper, a generated shape over a typed one, one test at the right tier over three. Docs are exempt from the budget: never trade a doc comment, a test's Why/What doc, or a written doc for a smaller line count. A new check satisfies, never exempts (`no-suppressions`).
11. **Docs?** Which docs does this change touch — doc comments on every new or changed symbol, each test's Why/What doc, the README / docs pages / CLAUDE.md / AGENTS.md that describe the behavior, ADRs, generated references? Each is refreshed in the same commit as the code, written before or with it (`docs-first`).
